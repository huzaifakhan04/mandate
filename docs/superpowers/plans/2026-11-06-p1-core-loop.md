# P1 Core Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any AI agent, using only the MCP URL or the REST API, can do four things:
- register;
- fund the bank by buying lender notes (paid with PayPal);
- borrow $10–$500 against an invoice, with the loan disbursed by PayPal Payouts;
- repay, either when the agent's client pays a bank-issued PayPal payment link or directly. Note holders then earn their share.

This is proven on real PayPal sandbox and by headless Claude agents, 3 out of 3 runs.

**Architecture:** This builds on P0 (see `docs/superpowers/plans/p0-carry-forward.md`).
- **Tools:** each new tool is a `defineTool` contract. Its domain service runs inside `runTool`'s per-call transaction: it changes rows, posts the journal and enqueues PayPal operations.
- **PayPal side effects:** these run after the transaction commits, through `executeOperation`. They are confirmed by verified webhooks **and** by a reconcile cron.
- **Human approvals:** a payer must approve some steps on a PayPal page. These are surfaced as `next_actions` of type `human_approval`. An agent then calls `confirm_checkout`.

**Tech Stack:** P0 stack, plus `uuid` (v5) for derived operation ids. There are no new runtime services.

**Spec:** `docs/superpowers/specs/2026-11-05-mandate-design.md`. Domain research is in `docs/research/agentic-bank-research.md`. The P0 review carry-forward is in `docs/superpowers/plans/p0-carry-forward.md`.

## Global Constraints
- All P0 Global Constraints still apply. Key ones:
  - integer cents (bigint);
  - `world_id` on every row;
  - `PayPal-Request-Id` = operation id;
  - secrets only in env;
  - no secret ever logged;
  - the envelope `{status, summary, reason_codes, data, next_actions, docs_url}`;
  - the light-theme tokens;
  - the commit trailers.
- **Money movement rule:** never call PayPal inside a DB transaction. Inside the transaction, call `enqueueOperation(tx, …)`. After commit, call `executeOperation(db, opId)`. The reconcile cron retries anything still queued or retryable.
- **Operation ids:** `deriveOperationId(worldId, purpose, sourceId)` is UUIDv5 using namespace `6f1c2a9e-5b7d-4c3e-9a1f-2d8e7b6c5a40` over `${worldId}:${purpose}:${sourceId}`. The **same** string `${purpose}:${sourceId}` is the journal `idempotencyKey`.
- **Purposes:** `note_purchase`, `note_redemption`, `loan_disbursement`, `repayment_link`, `repayment_direct`, `repayment_capture`, `note_purchase_capture`, `remainder_payout`.
- **API keys:**
  - format `mnd_<prefix8>_<secret32>`, where prefix and secret are base32-lowercase;
  - stored as `prefix` plus `sha256(API_KEY_PEPPER + secret)` hex;
  - shown once;
  - sent as `Authorization: Bearer <key>` (REST) or the same header on the MCP HTTP request.
- **P1 activation:** `ALLOW_INSTANT_ACTIVATION=true` (P1 default). `register_agent` returns an ACTIVE agent plus its key in the main world. Claim and mandate flows arrive in P2.
- **Fixed P1 pricing** (replaced in P3):
  - `fee_cents = min(2500, ceil(principal_cents × 150 × ceil(term_days/7) / 10000))`;
  - APR in bps = `round(fee/principal × 365/term × 10000)`;
  - principal 1000–50000 cents;
  - term 7–30 days;
  - one open loan per agent;
  - the offer expires after 1 simulated day.
- **Note economics:**
  - one note series per world, `Mandate Pool A`;
  - units = cents invested;
  - on each repayment, the fee splits 80% to note holders, pro rata by units at repayment time with largest-remainder rounding, and 20% stays with the bank;
  - holders' share credits `notes_payable[holder]` (added interest);
  - redemption ≤ the holder's balance and ≤ available liquidity.
- **Available liquidity** = `cash_paypal` balance − Σ(principal of loans in DISBURSING) − Σ(pending redemptions).
- **Chart of accounts additions (Task 4):** `note_interest_expense` (expense).
- **Journal templates** (Dr positive / Cr negative):
  - **Note purchase captured:** Dr `cash_paypal` A / Cr `notes_payable[agent]` A.
  - **Loan disbursed** (payout SUCCEEDED): Dr `loans_receivable` P / Cr `cash_paypal` P.
  - **Repayment captured, gross G ≥ P+F:**
    - Dr `cash_paypal` G
    - Cr `loans_receivable` P
    - Cr `fee_income` F
    - Cr `payable_to_borrower[agent]` (G−P−F) when > 0
  - **Holders' share:** Dr `note_interest_expense` H / Cr `notes_payable[holder_i]` h_i (Σh_i = H = floor(F×80/100)).
  - **Remainder paid out:** Dr `payable_to_borrower[agent]` R / Cr `cash_paypal` R.
  - **Note redeemed** (payout SUCCEEDED): Dr `notes_payable[agent]` A / Cr `cash_paypal` A.
- **Human-approval next action:** `{ "tool": "human_approval", "args": { "url": "<PayPal approve url>", "who": "payer|client", "then": { "tool": "confirm_checkout", "args": { "checkout_id": "…" } } } }`. Every tool response that needs a human puts this first.
- **Rate limits:** P1 has none (they arrive in P8). **Webhooks:** must be verified (Task 8).

## Review Focus
1. **The same mutating call is retried with the same `idempotency_key`** (REST header `Idempotency-Key` or arg `idempotency_key`). It must return the identical stored envelope, with no second journal and no second PayPal op. Different input under the same key → 409 envelope `IDEMPOTENCY_CONFLICT`. *Test in Task 1.*
2. **A webhook and the reconcile cron both process the same capture or payout.** Effects must happen exactly once: one journal, one remainder payout, one status change. *Test in Task 8.*
3. **The client pays the invoice link when no agent is online.** The bank must still capture, run the waterfall and pay the remainder automatically, via webhook or cron. *Test in Task 10.*
4. **Concurrent `accept_offer` calls from two agents could exceed available liquidity.** Liquidity must be checked under a row lock (`SELECT … FOR UPDATE` on the world's note series row) so the pool is never over-committed. *Test in Task 6.*
5. **A payout fails or goes UNCLAIMED** (the agent's PayPal email doesn't exist). The loan must go to DISBURSEMENT_FAILED with no `loans_receivable` booked and the agent told why. A failed redemption leaves the note balance intact. *Test in Task 6/8.*

  - `hashSecret(secret: string): string`

    5. After commit, run `ctx.afterCommit` callbacks (handlers register `executeOperation` calls there). Errors in them are logged and do not change the envelope.
    6. Catch-all → 500 `INTERNAL_ERROR`.
  - REST: `GET` is allowed for `readOnly` tools. Headers are read from `Authorization` and `Idempotency-Key`.
  - MCP: the route forwards the HTTP `Authorization` header (via the mcp-handler request context) into runTool. The `idempotency_key` arg works there too.

### Task 2: Queued PayPal operations and derived ids (carry-forward I1 + I4)

**Files:**

- Create: `src/server/paypal/operations.ts`, `src/server/paypal/operationId.ts`, `tests/unit/paypal/operations.test.ts`

**Interfaces:**
- Produces:
  - **`deriveOperationId(worldId, purpose: OperationPurpose, sourceId): string`** (UUIDv5, as in Global Constraints) and **`journalKey(purpose, sourceId): string`**.
  - **`enqueueOperation(tx, { worldId, rail: 'paypal'|'sim', kind, purpose, sourceId, request: { method, path, body } }): Promise<{ operationId }>`**. It is idempotent on the derived id, and a kind/rail mismatch throws `PayPalOperationReuseError`.
  - **`executeOperation(db, operationId): Promise<OperationResult>`**:
    1. **Claim** atomically: `UPDATE … SET status='in_flight', claimed_at=now() WHERE id=$1 AND status IN ('queued','failed_retryable') AND (claimed_at IS NULL OR claimed_at < now()-interval '2 minutes') RETURNING`. No row → return the current row's result (replay or someone else's in-flight attempt).
    2. **Call:** `paypalFetch` with that `operationId`.
    3. **Classify:** 2xx → `succeeded`; 4xx other than 401/409/429 → `failed_terminal`; 5xx, network error or timeout → `failed_retryable` with `next_attempt_at` = now + 30s·2^attempts (capped at 10 min).
    4. Return `{ status, body, httpStatus }`.
  - `paypalFetch` keeps its contract but documents and enforces "not inside a transaction" with a cheap guard: `txDepth` on a Drizzle tx is unknowable, so put a JSDoc rule plus a unit test that the service code only calls `executeOperation`.
  - **`orders.capture` accepts `operationId`.** A 422 `ORDER_ALREADY_CAPTURED` → GET the order and return the completed capture (treated as success).
  - **The rail interface** gains `captureCheckout({ …, operationId? })`. The sim rail mirrors `executeOperation` semantics so services are rail-agnostic. Add `executeOperationViaRail(db, rail, opId)`, or have `enqueueOperation` record the rail and have `executeOperation` dispatch to the sim rail when `rail='sim'`.

### Task 7: Repayment: invoice payment link, repay_loan, waterfall, remainder payout, note distribution, get_statement

**Files:**
- Create: `src/server/domain/waterfall.ts`, `src/server/domain/distribution.ts`, `src/server/services/repayments.ts`, `src/server/contracts/tools/{repayLoan,getStatement}.ts`, `tests/unit/domain/waterfall.test.ts`, `tests/unit/domain/distribution.test.ts`, `tests/unit/services/repayments.test.ts`

**Interfaces:**
- **`waterfall({ grossCents, principalCents, feeCents }): { principal, fee, remainder, shortfall }`**:
  - gross < P+F → partial: fee first, then principal, `shortfall` > 0, and the loan stays ACTIVE with outstanding reduced;
  - gross ≥ P+F → REPAID and remainder = G−P−F.
- **`distribute(holderUnits: {agentId, units: bigint}[], amountCents: bigint): {agentId, cents: bigint}[]`**: pro rata with largest remainder, Σ = amount. Golden: units [3,3,3] with amount 10 → [4,3,3] (the first id in a stable sort by agentId gets the extra cent).
- **Repayment link:** created when a loan with an invoice becomes ACTIVE.
  - It enqueues `checkout_create` with purpose `repayment_link` and sourceId = loanId, for **the invoice amount**, payee = the bank (default merchant), description `Invoice <description> — pay to Mandate on behalf of <agent name>`.
  - A `repayment_links` row stores the url.
  - `get_loan` shows the link, and the agent forwards it to its client.
- **`repay_loan`** (agent, mutating): input `{ loan_id, amount_cents? }` (default outstanding) → a direct checkout (purpose `repayment_direct`) → `human_approval` + `confirm_checkout`.
- **`applyRepaymentCapture(db, captureResult, linkOrCheckout)`**:
  1. One journal per capture.
  2. Posts the repayment journal template.
  3. Enqueues the remainder payout (`remainder_payout`, sourceId = repayment id) when remainder > 0.
  4. Posts the holders' share with `distribute`, over positions at that moment.
  5. Marks the loan REPAID.
  6. Appends events.
  7. Is idempotent by `journalKey('repayment_capture', captureId)`.
- **`get_statement`** (agent, readOnly) → data `{ notes: {balance_cents, earned_cents}, loans: [...], ledger_lines: [{sim_at, memo, account, amount_cents}] }`, the agent's own sub-accounts only.
